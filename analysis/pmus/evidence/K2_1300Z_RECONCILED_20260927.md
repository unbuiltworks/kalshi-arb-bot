## The defect that produced the incoherent book

The executor's own parked-order resolution, 13:11:16Z:

```
PENDING_TERMINAL_RESOLVED  coid CREX7ZDP2YC6
  already 0   cum 0   delta 0   terminal true   state "ORDER_STATE_NEW"
  avg_px 0.0000   cum_qty 0   released true   resolved true
  labels "final fill booked from the venue's own order row; this is the
          reconstruction that resolves a lost cost basis, not an assumption"
```

The order had already filled at `lastTransactTime 13:09:06` — two minutes
earlier. The venue served a row reading `state ORDER_STATE_NEW`,
`cumQuantity 0`, `leavesQuantity 0` for an order of `quantity 0.9`.

**That row is self-inconsistent**: `cum 0 + leaves 0 ≠ quantity 0.9`. Nothing
can be simultaneously unstarted, fully resolved, and 0.9 in size.

`l5_live_execution.order_progress` decides terminality on `leavesQuantity`
alone:

```python
if has_leaves:
    terminal = leaves <= 0
```

so it accepted `leaves == 0` as terminal, booked `cum_qty 0` as the final
fill, released the order — and emitted a label asserting this was read from
the venue rather than assumed. **The label was wrong.** The same happened to
`CREWYQ75RYCA`, and to both client-id twins.

The fix is small and local: refuse a row where
`cum_qty + leaves_qty != quantity`, park it and stay uncertain rather than
booking a zero fill. That is the direction this code already says it wants to
be stuck in. It is a correctness defect in the execution core, identified by
live evidence.

## Why it happened when it did

At the 1300z window close, one log record carries **~2,440 order operations
refused locally with `VenueThrottled`** — the known P1 cooldown busy-wait,
firing exactly when orders needed resolving. The registered request-budget
priority puts parked-order resolution FIRST; what actually happened is that
order resolution was starved while the limiter spent the budget refusing
its own retries.
