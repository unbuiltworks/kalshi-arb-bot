## What worked

**The quantization did its job.** This is the first order this system has
ever got past the venue's preview: the quantity was floored onto the venue's
own increment, previewed, echoed exactly, and posted. `preview accepted 1 /
refused 0`, where Probe 03 was `0 / 1`. `submit_failures` is empty — nothing
raised inside `submit()`.

Every pre-arm condition held: `preflight PASSED`,
`api_key_fingerprint d51b44a3fa83`, `account_matches_expected true`, the
quantity increment established, book fresh (8962 frames, age 0.287s).

`MAX_LIVE_ORDERS` refused 29 subsequent actions — the one-live-order cap
worked exactly as written, which is why exposure stayed at one order.

## What failed, and it is the important part

Two defects, both in the close-out path, both first reachable **only once an
order actually existed** — which had never happened before:

1. **`cancel()` raised HTTPError.** `POST /v1/order/{id}/cancel` at
   ~13:13:30Z, while the market was still open (expiry 13:15:00Z). The status
   code is in the journal on the volume, not in this report — `cancel_errors`
   records only the exception class.
2. **`reconcile_from_venue()` raised TypeError.** Almost certainly a shape
   mismatch: it does `p["market"]` over `positions()`, and if the venue
   returns positions as a mapping rather than a list of rows, iteration
   yields strings and `p["market"]` is `TypeError: string indices must be
   integers`. Every previous call returned empty, so the populated shape had
   never been exercised.

The design held around both: exposure was **not** released, the store is
marked uncertain, and the report says so rather than claiming a clean finish.
