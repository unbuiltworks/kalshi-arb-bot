# CORRECTION — 2026-09-14T10:45Z

**Two claims above are wrong and are left standing with the correction beneath
them, because they are what was reported.**

## 1. "Collection has stopped" / "67 minutes of silence" — WRONG

The probe has **never been silent**. It has been logging continuously since the
HALT, every ~90 seconds:

```
PMUS_L5_CAMPAIGN {"kind":"campaign_iteration_error","commit":"75edc4bdcbe3",
 "err":"Halt:GET_RETRIES_EXHAUSTED:/v1/orders/open:HTTP Error 503: Service Unavailable",
 "errors_in_window":20,"max_in_window":1000000000,
 "outage_class":"unplanned","overrun_s":null}
```

Continuous and unbroken from **09:25:45Z through 10:41:41Z** — verified at
10:05, 10:06, 10:08, 10:09, 10:11 and every cycle to 10:41. My earlier log
query filtered on `flat_verified`, which `campaign_iteration_error` rows do not
contain, so it returned nothing and I read that absence as silence. That was a
filter artefact, not a fact about the probe.

## 2. "Halted and idle" / CPU 0.0006 — MISREAD

The 0.0006 CPU figure was a five-minute-average sample, not evidence of an
inactive process. The probe is in its **campaign retry loop**, re-attempting
the authenticated read every cycle and refusing to proceed each time.

## What is actually true

**The read-only authenticated reconciliation is already running, on the
production service's own credential path, every ~90 seconds — and it is
failing.** That failure IS the answer to "establish current state": it cannot
be established, because the only authenticated path available cannot read
`/v1/orders/open`.

**The outage is NOT venue-wide.** The recorder's authenticated WebSocket
market-data feed is healthy at the same moment — CPU 0.147, NETWORK_RX 0.336 GB
current, 0.685 GB average. The failure is specific to the **REST
`/v1/orders/open`** endpoint.

**Duration: ~76 minutes and ongoing** as of 10:41:41Z.

**`max_in_window` is 1000000000** — the error budget is effectively unlimited
by design, so a long outage cannot make the probe self-disarm. It will keep
retrying and **will resume on its own the moment the venue answers**. No human
restart is required for recovery.

## Verdict: REMAIN HALTED

Per the standing decision rule — *if authenticated state is still unreadable or
contradictory, remain HALTED and surface the exact unresolved condition; do not
trade* — the state is still unreadable, so:

- **no restart, no redeploy, no config or variable change, no credential
  touched, no order cancelled or placed;**
- **RECOVERY_FLAT is NOT declared** and cannot be: authenticated venue state is
  unavailable, so it cannot agree with ledger state;
- **the ten orders last seen `still_open` + `unreadable` remain UNKNOWN.**

Restarting would be actively worse than waiting. The boot path would hit the
same 503, and `shutdown_idle`'s own comment records why a process that exits is
dangerous here: *"To the platform a long-running service that exits is a CRASH,
and the platform's repair for a crash is to roll back to the PREVIOUS
deployment"* — which could restore a build that is ARMED. Staying up and
retrying is the designed behaviour and it is working.

## Classification

**VENUE_TRANSIENT_503 / FAIL_CLOSED.**

The GET retry and fail-closed behaviour performed exactly as intended: it
refused to trade against a book it could not read, it did not place or cancel
anything blind, and it kept the process alive and legible. **No change to retry
counts, backoff, or the fail-closed predicate is proposed. Uptime is not a
reason to weaken a gate whose entire purpose is to stop here.**
