## 2. The approval document

Generated by `tools/make_campaign_approval.py`, outside the executor.
`EnvApprovalStore.put` refuses by design: *the executor may not write its
own approval.*

The document asks for exactly the approved figures. The gate grants the
**intersection** of the document and the code ceilings, and reports every
field it clamped — a document asking for more yields less, never more.

The nonce is written to a 0600 file and never printed. The document is
identified everywhere — stdout, heartbeat, claim ledger — by its
**sha256 digest only**.

One change was needed to make the approved duration real: `campaign_decision`
now builds the gate with `max_age_s=MAX_CAMPAIGN_S` instead of the 1-hour
`DEFAULT_MAX_AGE_S`. That default exists so a forgotten *pull* endpoint
cannot keep authorizing; applied to a variable the owner sets deliberately it
would have cut the approved four hours to one and put the owner back to
re-issuing by hand every hour. The hard bound is untouched: the effective
expiry is still clamped to `issued + 4h`.

## 3. Automatic window advancement

No Railway edit per window. Each window:

1. the runner discovers the next BTC15m slug and binds the session to it;
2. `campaign_decision(slug)` reads the document, checks the series and
   expiry, and **reserves the window durably** in
   `$L5_LIVE_ROOT/campaign_windows/<nonce_sid>.json` before anything arms —
   a crash costs a window rather than granting one;
3. re-arming inside an already-reserved window resumes it and does not
   spend a second;
4. the verdict is passed into `authorize_arming(campaign=...)` as a fact.
   Absent → the single-window handshake is untouched. Present and not ok →
   **refuse**; the single-window path is never a fallback.

Consumption survives a redeploy because it is on the volume, keyed by the
nonce. A new nonce gets its own budget; the old nonce's spent windows stay
spent.

## 5. Automatic stop conditions

The campaign stops itself, with no intervention, on any of: windows
exhausted; submissions exhausted; `issued + 4h` passed;
`L5_LIVE_AUTH_NOT_AFTER` passed; daily realized loss ≤ −$5; cumulative loss
gates; halt latch set; reconciliation failure; unresolved accounting;
orders-uncertain; exposure or residual cap; cash gate; pair cost above
$0.96; or the document being cleared from the variable.

## 6. Per-window report (what will be published for each)

submitted orders (venue IDs) · exchange-confirmed fills only · actual pair
cost from fill prices · unmatched inventory · settlement P&L · cumulative
realized net. A submitted complement is **not** a hedge; only
exchange-confirmed fills count, and only settlement is labelled realized.
